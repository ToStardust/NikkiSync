# NikkiSync M0.16 + M0.17 + M0.18

## 本轮完成范围

### M0.16 Sample Analyzer

可运行的纯 Node.js CLI：

- 递归扫描真实暖暖样本目录；
- 路径分类与 UID 推断；
- SHA-256；
- JPEG/PNG 尺寸；
- EXIF/XMP/Motion XMP 标记；
- JPEG `FFD9` 位置与 EOI 后尾数据统计；
- ffprobe 视频 codec / fps / duration / audio / creation_time；
- HighQuality ↔ LowQuality 候选；
- 静态图 ↔ motion video 候选评分；
- JSON + Markdown 双报告。

**M0.16 尚未做的事情：** 直接调用暖暖参数解密 DLL。真实样本报告确定“是否必须依赖内部 asset id”后，再接 `NikkiMetadataDecoderAdapter`，避免第一轮调查被某个外部二进制绑定。

### M0.17 SQLite Schema

核心从“file-centric”改为“asset-centric”：

```text
assets 1 ── N resources
```

并新增：

- `resolver_candidates`
- `change_journal`
- `paired_devices`
- `device_sync_state`
- `pairing_sessions`
- `library_state`

所有远程图库可见变更都走 monotonic revision transaction。

### M0.18 Protocol TypeScript Contract

冻结 Protocol v1 的：

- Asset / Resource / MotionAssetInfo
- InfinityPhotoMetadata v1
- TemplatePhotoContext
- HTTP route constants
- cursor pagination
- changes/revision
- WebSocket events
- pairing DTO
- Ed25519 request auth headers
- protocol error codes

## 与 NikkiGallery 的关系

复用/参考：游戏目录发现、UID discovery、参数解密、缩略图/视频工具、XMP 设计、SQLite worker 化经验。

不沿用：`media_files` 的“一文件一记录”作为 NikkiSync 主域模型。NikkiSync 从 M0 开始以 Asset 聚合多个物理资源，这是支持游戏实况照片和 High/LowQuality 变体的必要条件。

## 实况照片规范约束

PC 只存/同步游戏源 still + motion。最终封装发生在手机：

- iOS：构建 Photos 可识别的 Live Photo pair；Apple 文档规定 movie 中的 QuickTime Content Identifier 与 still image MakerNote 中的对应 identifier 关联。
- Android：构建 Motion Photo 1.0；官方规范定义 primary still + appended video，并由 Camera/Container XMP 描述 motion 标志、presentation timestamp 和视频长度/位置。

因此 `MotionAssetInfo.presentationTimestampUs` 是跨平台 canonical 字段，不把 Apple/Android 私有封装细节写入 PC Asset 模型。

## M0.16 真样本验收门槛

至少准备：

- 普通照片 3 组；
- 实况照片 3 组；
- 每组尽量保留 HighQuality + LowQuality；
- 实况对应 Video 原文件；
- 不要经过微信/网盘压缩或图片编辑器二次保存。

报告后必须能回答：

1. 静态图与视频是否存在确定性共同 ID？
2. High/Low 是否存在确定性共同 ID？
3. JPEG EOI 后 payload 是否稳定存在，长度/结构是否与拍摄类型有关？
4. mtime/birthtime/视频 creation_time 哪一个最接近真实配对时间？
5. 实况 still 是否就是 HighQuality 原图，还是必须从视频选帧？
6. 若只能启发式匹配，怎样设自动接受阈值才能避免错配？
